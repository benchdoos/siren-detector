# Архитектура

## Целевая схема заменяемых компонентов

```text
Аудиоисточники → адаптеры входа → Runtime Hub ──аудио──→ цепочка обработки
                                        ↑                 DSP → YAMNet → MLP
                                        └──── оценки / события ────┘
                                        │
                                        ├→ score-экспорт / мониторинг
                                        └→ политика событий → слой экспорта
                                                               ├→ Web UI / WS
                                                               ├→ REST API
                                                               ├→ MQTT и другие выходы
                                                               └→ клипы / хранилище
```

Это целевая архитектура, а не описание полностью реализованного состояния.
Основной принцип: у каждого блока есть контракт, поэтому можно заменить
источник, маршрутизатор, этап обработки или выходной адаптер независимо от
остальных блоков. Например, пользователь сможет заменить MLP, всю цепочку
распознавания или способ публикации событий, не переписывая микрофон и UI.

Слово «Hub» сейчас означает UDP fan-out relay в `hub/hub.py`: он пересылает
пакеты детектору и рекордеру. В целевой схеме Runtime Hub — логический
маршрутизатор внутри Detector: он направляет аудио по цепочкам, принимает
результаты обработки и передаёт их в политику событий и слой экспорта. Это
разные роли; не следует смешивать их в документации или контрактах.

## Текущий путь аудио и событий

```text
INMP441 → ESP32-S3 → UDP / SDR1 → UDP Hub → Detector → Web UI / MQTT
                                             └──────→ клипы событий
```

Текущий UDP Hub — небольшой сетевой ретранслятор. `UDPSourceAdapter` в Detector
декодирует SDR1 и выдаёт `AudioFrame`; Runtime Hub направляет кадр подписчикам.
YAMNet engine подписывается на кадры через отдельную ограниченную очередь;
Runtime Hub не ждёт callback обработки. Engine сам управляет буферами,
инференсом и сглаживанием событий. Его оценки и события проходят обратно через
Runtime Hub в legacy EventBus, на который подписаны WebSocket и MQTT.

## Компоненты

| Компонент | Назначение | Код и настройки |
|---|---|---|
| Аудиоузел | Получает звук с частотой 16 кГц и отправляет SDR1-пакеты | `esp32/siren-detector.yaml` |
| UDP Hub | Пересылает каждый пакет настроенным получателям | `hub/hub.py`, `hub/docker-compose.yml` |
| Runtime Hub | Маршрутизирует нормализованные аудиокадры и результаты обработки | `detector/runtime/` |
| Detector | Держит входной UDP-адаптер, буферы, обработку, UI/API и интеграции | `detector/` |
| Recorder | По запросу записывает аудио в WAV по папкам меток | `recorder/` |
| Инструменты ML | Готовят данные, обучают классификаторы и оценивают модели | `dataset/`, `ml/` |

## Текущий конвейер детектора

Текущий движок использует отдельный YAMNet + MLP inference stage; DSP/TFLite остаётся предварительным фильтром. Stage возвращает `inference-result.v1` через Runtime Hub. `EventPolicy` применяет пороги и сглаживание, а запись клипов передаёт через Hub в `WavClipStorage`. Legacy score/event идут через Hub в `EventBusOutput`. Политику можно выбрать как `default` или передать локальный Python-класс через CLI; контракт `event-policy.v1` уже есть, но его контекст пока содержит внутренности Detector.

Python-пакет разделён на транспорт, engine, сервер и интеграции, связанные
`EventBus`. Однако это пока не означает, что любой слой уже можно подменить
через стабильный внешний API: `EngineInterface.start()` получает Runtime Hub,
settings и CLI args. `main.py` регистрирует UDP-адаптер, engine подписывается
на кадры, а результаты проходят обратно через Hub и `EventBusOutput` в
`EventBus`. Буферы и DSP-предобработка пока остаются внутри engine; инференс
вынесен в `detector/engine/stages/yamnet_mlp.py`, политика событий — в
`detector/engine/event_policy.py`.
Формат legacy-сообщений описан в коде и частично в
[`detector/engine/interface.py`](https://github.com/benchdoos/siren-detector/blob/main/detector/engine/interface.py), но ещё
не является версионируемым публичным контрактом.

При непустом `engine_configs` запускается сохранённый `engine-graph.v1`:
каждый назначенный маршруту движок стартует один раз со своими settings, а
Runtime Hub применяет `default`/`by_source` к его аудиоподписке. Граф действует
после перезапуска. Явный `--engine` при активном графе отклоняется. Один Python
класс нельзя назначить под несколькими `engine_id`, так как manifest, runtime
подписка и ключ event policy используют уникальный ID. В graph mode настройки и
smoothers YAMNet изолированы в его записи, а event policy получает её settings.
Settings UI управляет графом и показывает lifecycle/ошибки рядом с карточкой
движка; отдельная Runtime panel показывает здоровье аудиоподписок. Та же
конфигурация доступна через REST API.

Целевое разделение границ и форматов описано в [API компонентов](component-api.md).
HTTP и WebSocket API приложения описаны отдельно в [справочнике API](api.md),
а текущие runtime-параметры — в [справочнике настроек](settings.md).

## Аудиопротокол

SDR1 состоит из 12-байтового заголовка в сетевом порядке байтов и PCM-данных:

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 байта | Магическое число `0x53445231` (`SDR1`) |
| 4 | 4 байта | Последовательный номер пакета |
| 8 | 2 байта | Размер данных в байтах |
| 10 | 2 байта | ID источника |
| 12 | переменный | PCM-данные |

Данные передаются в формате I2S: моно, 16 кГц, 32-битные слоты. Приёмник разделяет источники по ID и создаёт для каждого собственные буферы и сглаживатели.

## Несколько микрофонов: текущее поведение

Прошивка ESP32 получает звук с двух необязательных INMP441 на отдельных шинах I2S, затем усредняет отсчёты и отправляет один поток SDR1. Поэтому для детектора они выглядят как **один источник**. USB-микрофон с `audio_source/audio_source.py` работает как отдельный источник. Подробности — в разделе [Несколько микрофонов](multi-microphone.md).

## DSP-каскад (предварительный фильтр)

Детектор может запускать лёгкую DSP-модель перед YAMNet, чтобы пропустить дорогой инференс, когда аудио явно фоновое.

### Как это работает

```text
Аудио (0.5 с) → Извлечение DSP-фич → Conv1D классификатор → Решение
                                                               │
                                        background (высок. уверенность) → пропуск YAMNet
                                        что-то другое                   → запуск YAMNet + MLP
```

**Шаг 1: Извлечение фич** (`detector/dsp_features.py`). Восемь микрофонно-инвариантных признаков извлекаются из каждого 40-мс фрейма (20 мс hop, 50 fps):

| Признак | Что улавливает |
|---|---|
| Pitch (YIN) | Основная частота — у сирен характерные паттерны свипа |
| Log RMS energy | Громкость — взрывы дают резкие скачки энергии |
| Spectral centroid | «Яркость» звука |
| HNR (отношение гармоник к шуму) | Тональный vs шумовой — сирены тональные, фон шумной |
| ZCR (частота пересечения нуля) | Косвенная оценка частотного содержания |
| Spectral bandwidth | Насколько энергия распределена по частотам |
| Spectral flatness | Шумоподобный vs тональный спектр |
| Spectral rolloff | Частота, ниже которой сосредоточено 85% энергии |

Дельта-признаки (скорость изменения) добавляются, итого 16 признаков на фрейм.

**Шаг 2: Conv1D классификатор** (`detector/dsp_infer.py`). TFLite-модель обрабатывает 250 фреймов (5 секунд) нормализованных признаков. Архитектура: Conv1D(24, k=7) → Pool → Conv1D(48, k=5) → Pool → Conv1D(48, k=3) → GlobalAvgPool → Dense(48) → Dense(4). Всего: ~18K параметров, ~30 КБ в INT8 TFLite.

**Шаг 3: Решение гейта**. Если DSP-модель предсказывает "background" с уверенностью выше `dsp_bg_threshold` (по умолчанию 0.92), YAMNet-инференс пропускается для этого окна. Гистерезисный механизм предотвращает быстрые переключения:

- `dsp_bg_confirm_windows` (по умолчанию 2): нужно столько последовательных предсказаний "background" для начала пропуска.
- `dsp_bg_release_threshold` (по умолчанию 0.90): уверенность должна упасть ниже этого порога для возобновления YAMNet.
- `dsp_event_gate` (по умолчанию 0.30): если вероятность любого класса событий превышает этот порог, YAMNet запускается в любом случае.
- `dsp_max_consecutive_skips` (по умолчанию 20): предохранитель — после N последовательных пропусков выполняется принудительный проход YAMNet, чтобы DSP-модель не блокировала обнаружение навсегда.

### Почему DSP-фичи инвариантны к микрофону

В отличие от спектрограммного подхода, который зависит от АЧХ микрофона, DSP-фичи (pitch, HNR, ZCR) описывают структурные свойства звука. Смена микрофона или места смещает абсолютные уровни, но сохраняет паттерны, отличающие сирены (периодический свип), взрывы (резкий энергетический всплеск) и БПЛА (устойчивая тональная энергия) от фонового шума.

### Настройка

Параметры DSP — в [Настройках](settings.md#dsp-предфильтр). Per-source overrides позволяют задавать разные пороги для разных микрофонов. DSP-модель должна присутствовать в директории моделей; при отсутствии фильтр автоматически отключается.

## Режимы распознавания

Detector поддерживает режим `round_robin` (один цикл последовательно обрабатывает активные источники) и `parallel` (отдельный цикл для каждого источника). Параллельный режим может уменьшить задержку отдельного источника, но увеличивает потребление процессора и памяти с ростом числа источников. Режим выбирается в настройках детектора. Ни один из режимов не выполняет распознавание на ESP32. Подробнее: [режимы и настройки](settings.md#режимы-обработки).
