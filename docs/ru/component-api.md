# API компонентов

Этот документ описывает целевую архитектуру подключаемых компонентов. Это
проектируемый контракт: текущий код ещё не реализует все перечисленные
интерфейсы и форматы. HTTP API веб-приложения описан отдельно в [API](api.md).

## Цель и термины

Система собирается из заменяемых блоков:

```text
источники → адаптеры входа → Runtime Hub ⇄ цепочки обработки
                                  │       DSP → YAMNet → MLP
                                  └→ слой экспорта → UI / WS / REST / MQTT
```

Любой блок можно заменить реализацией, которая соблюдает контракт своего типа.
Пользователь может заменить один этап (например, MLP), всю цепочку распознавания,
источник аудио, маршрутизацию или выход, не связывая новый компонент напрямую
с кодом остальных.

Термин **Runtime Hub** здесь означает логический маршрутизатор внутри Detector.
Существующий **UDP Hub** (`hub/hub.py`) — отдельный сетевой ретранслятор,
который прозрачно пересылает UDP-пакеты. Это разные компоненты.

### Типы компонентов

| Тип | Вход | Выход | Примеры |
|---|---|---|---|
| Источник | Микрофон, файл или сетевой поток | Аудиоданные | ESP32/SDR1, USB/ALSA, файл |
| Адаптер входа | Протокол или драйвер источника | Общий `AudioFrame` | SDR1/UDP → PCM кадры |
| Runtime Hub | Кадры и конфигурация маршрутов | Направленные кадры/запросы | Fan-out, выбор цепочки |
| Этап обработки | Кадр либо результат предыдущего этапа | Преобразование или оценка | DSP, YAMNet, MLP, пользовательская модель |
| Политика событий | Оценки одного или нескольких этапов | Нормализованные события | Порог, temporal smoothing, объединение |
| Выходной адаптер | Нормализованные оценки/события | Внешнее представление | WebSocket, MQTT, webhook, клипы |

Драйвер микрофона нужен источнику/адаптеру входа, а не модели, которая получает
уже нормализованные кадры. Для LLM или удалённой модели может понадобиться
отдельный processing adapter, например пакетирование звука или передача
транскрипции/сводки, но это не меняет аудиодрайвер.

## Границы и ответственность

### Аудиоисточник и адаптер входа

Адаптер отвечает за особенности устройства и протокола: получение данных,
декодирование, преобразование формата и назначение стабильного `source_id`.
Он не принимает решение о наличии сирены и не публикует MQTT напрямую.

Внутренний контракт аудио должен нормализовать формат независимо от транспорта.
Начальный профиль проекта: mono, 16 kHz, float32 PCM внутри Detector. Адаптер
может принимать другой формат и привести его к этому профилю. Оригинальные
параметры источника сохраняются в metadata. Текущий SDR1/UDP остаётся одним из
адаптеров; wire format SDR1 не подменяет общий внутренний контракт.

Предлагаемая форма кадра:

```json
{
  "contract": "audio-frame.v1",
  "source_id": "0",
  "sequence": 1842,
  "timestamp": "2026-10-21T10:15:30.125Z",
  "sample_rate_hz": 16000,
  "channels": 1,
  "sample_format": "float32",
  "samples": "binary payload",
  "metadata": {"transport": "sdr1/udp"}
}
```

В реальном API массив `samples` должен передаваться бинарным блоком или через
внутренний объект, а не кодироваться в JSON. Кадр содержит достаточно времени
и sequence информации, чтобы обнаруживать разрывы и сохранять порядок.

### Runtime Hub / маршрутизатор

Runtime Hub работает в обе стороны:

1. Принимает аудиокадры от входных адаптеров и направляет их в назначенные
   цепочки обработки.
2. Получает от цепочек оценки, события и статус выполнения, связывает их с
   исходными `source_id`, frame и `engine_id`.
3. По конфигурации направляет результат в политику событий и/или слой экспорта.

Таким образом, модель возвращает информацию в Runtime Hub, а Hub передаёт её
дальше в выходной слой. Он может маршрутизировать промежуточные scores напрямую
для мониторинга, а итоговые события — через event policy, которая выполняет
пороговую обработку, temporal smoothing, дедупликацию и объединение. Runtime Hub
сам не содержит специфичную логику YAMNet, DSP, MQTT или правил конкретного
класса; его задача — маршрутизация, корреляция и lifecycle.

В первой версии маршрутизация может быть статической: источник назначен одной
или нескольким цепочкам. Динамические правила, условный запуск следующего этапа
и UI-конструктор графа — последующие возможности.

### Цепочка обработки

Обработка конфигурируется как упорядоченный список компонентов. Профиль по
умолчанию сохраняет текущую функциональность:

```text
DSP pre-filter → YAMNet embeddings/scores → MLP classifier → event policy
```

DSP, YAMNet и MLP — отдельные заменяемые этапы/модели; реализация может
объединить их внутри одного процесса ради эффективности, если снаружи сохраняет
тот же контракт. Цепочка может выдавать промежуточные оценки и конечный
результат. Общая event policy превращает оценки в состояния и события; позже
политика также сможет объединять вывод нескольких цепочек.

Обработчик получает аудиокадр и контекст вызова, возвращает результат с теми
же source/frame идентификаторами. Ему не следует напрямую обращаться к UI,
MQTT или файловой системе клипов. Специфичные ресурсы и приватное состояние
этапа остаются внутри этого компонента.

### Слой экспорта и выходные адаптеры

Слой экспорта получает нормализованные результаты, переданные Runtime Hub, и
преобразует их для конкретных получателей. Его адаптеры могут подписываться на
scores, события и состояние компонентов. WebSocket/UI — потоковая
визуализация, REST — чтение состояния и управление, MQTT/webhook — доставка
наружу, clip storage — хранение аудио. Сбой одного необязательного выхода не
должен останавливать аудиовход или инференс; для каждого выхода задаются
буферизация, повтор доставки и политика отбрасывания.

## Общий результат обработки

Все processing-компоненты публикуют оценки в общей форме. Конкретная схема
будет уточнена при реализации и версионирована; минимальная форма:

```json
{
  "contract": "inference-result.v1",
  "source_id": "0",
  "engine_id": "default-audio-chain",
  "frame_sequence": 1842,
  "timestamp": "2026-10-21T10:15:30.125Z",
  "stage_id": "mlp",
  "scores": {"siren": 0.87, "background": 0.08},
  "metadata": {"model_version": "local"}
}
```

Идентификаторы `engine_id` и `stage_id` нужны для атрибуции, но не должны
встраивать имена конкретных моделей в общий протокол. Оценка — это выход модели;
она сама по себе ещё не означает подтверждённое событие.

Событие создаётся политикой событий и содержит как минимум:

```json
{
  "contract": "detector-event.v1",
  "event_id": "unique-id",
  "class": "siren",
  "state": "confirmed",
  "confidence": 0.87,
  "timestamp": "2026-10-21T10:15:30.125Z",
  "source_id": "0",
  "engine_ids": ["default-audio-chain"],
  "evidence": [{"stage_id": "mlp", "score": 0.87}],
  "clip_url": "/clips/example.wav"
}
```

Для нескольких решений событие должно сохранять происхождение и evidence.
Правило подтверждения, дедупликации и объединения — часть конфигурации event
policy, а не скрытая логика UI или MQTT адаптера.

### Контракт политики событий `event-policy.v1`

Runtime Hub выбирает одну активную политику. Она получает каждый
`InferenceResult` через `process(result)` и публикует score/event через
`context.runtime.publish(RuntimeMessage)`. Реализация объявляет `policy_id` и
`api_version = "event-policy.v1"`. Текущую можно выбрать как `default`; локально
установленный Python-класс — передать через `--event-policy
package.module.ClassName`. Класс создаётся с `EventPolicyContext`, где доступны
Runtime Hub, реестр per-source состояния и необязательный DSP компонент.

```python
from detector.runtime.contracts import RuntimeMessage


class MyPolicy:
    policy_id = "my-policy"
    api_version = "event-policy.v1"

    def __init__(self, context):
        self.runtime = context.runtime

    def process(self, result):
        self.runtime.publish(RuntimeMessage.from_legacy({
            "type": "score",
            "top": "custom model",
            "source_id": result.source_id,
            "siren_score": result.scores.get("my-model:siren", 0.0),
        }))
```

Загрузка Python-классов рассчитана на локальную конфигурацию разработчиком;
загрузка или установка кода через UI не поддерживается. `EventPolicyContext`
сейчас содержит внутреннее состояние Detector и ещё не является переносимым
публичным SDK.

## Конфигурация и жизненный цикл

### Manifest решения `engine-manifest.v1`

Каждый зарегистрированный движок объявляет `ENGINE_MANIFEST` со стабильным `engine_id`, именем,
версией `MAJOR.MINOR.PATCH`, классами, входными/выходными контрактами,
JSON Schema настроек, требованиями к ресурсам и Python entrypoint. Для
встроенного решения manifest можно посмотреть командой
`python -m detector.main --engine yamnet --show-engine-manifest`. Сторонний
движок может объявить такой же `EngineManifest` в атрибуте класса. Пока manifest
не публикуется через API/UI, а схема настроек не управляет формой Settings.

Встраиваемое приложение может зарегистрировать short selector до запуска:

```python
from detector.engine.registry import engine_registry
from detector.main import main

engine_registry.register("my-engine", "mypackage.engine.MyEngine")
main()  # запускать с аргументом --engine my-engine
```

Зарегистрированный движок обязан объявить `ENGINE_MANIFEST`, а его
`engine_id` должен совпадать с selector. Список встроенных и зарегистрированных
имён можно вывести командой `python -m detector.main --list-engines`.

В текущем CLI можно также передать dotted path класса напрямую. Это сохраняет
совместимость со старым интерфейсом `start(runtime, settings, args)`; такой
класс без `ENGINE_MANIFEST` загружается с предупреждением. Реестр загружает
Python-код в том же процессе, поэтому пакет должен быть установлен локально.

Компонент должен объявлять стабильный ID, тип, версию, поддерживаемую версию
контракта, схему собственных настроек и возможности. Настройки разделяются на
общие, для источника, для компонента/этапа и для связи источника с цепочкой.
Секреты (токены внешних сервисов) хранятся отдельно от обычных параметров и
не возвращаются в открытом виде из API.

Минимальный lifecycle: `configured → starting → ready → stopping → stopped`,
с состоянием `error` и диагностикой при сбое. Компонент должен принимать
ограничения ресурсов и таймауты; остановка или падение одного компонента не
должны молча блокировать весь граф. Перезагрузка процесса может потребоваться
для смены некоторых компонентов, а динамическое применение настроек должно
объявляться явно.

Реестр компонентов и настройка графа — задача управляющего API. Не следует
считать произвольный Python import или загрузку пользовательского кода через
веб-интерфейс безопасным способом установки расширений. В MVP допустима
конфигурация разработчиком через файл/CLI; UI для установки и включения
компонентов добавляется после стабилизации контрактов.

## Версии и совместимость

- Контракты аудио, результата и события имеют независимые версии.
- Несовместимое изменение повышает основную версию контракта.
- Неизвестные необязательные поля игнорируются и сохраняются посредниками,
  если они пересылают сообщение без преобразования.
- Каждый адаптер объявляет поддерживаемые форматы и версии.
- До фиксации публичного `v1` схемы являются проектом; нельзя считать
  приведённые JSON-примеры готовым стабильным wire protocol.

## Текущая реализация и переход

Сейчас `detector/main.py` выбирает один engine через `--engine` и регистрирует
`UDPSourceAdapter` в Runtime Hub. Адаптер публикует `AudioFrame`; engine
подписывается на кадры, а YAMNet + MLP stage публикует `InferenceResult` с
`source_id`, `stage_id`, timestamp, namespaced scores и metadata обратно через
Hub. Текущая политика получает результат через Hub, применяет сглаживание и
публикует score/event в legacy-формате. Hub направляет итог в `EventBusOutput`,
который сохраняет старый формат для `EventBus` (`detector/bus.py`), WebSocket и
интеграций. Буферы и DSP-предобработка всё ещё находятся в `yamnet_engine.py`;
политика вынесена в `detector/engine/event_policy.py` и следует
`event-policy.v1`; сохранение WAV и sidecar проходит через `WavClipStorage` по
запросу Runtime Hub. Движки загружаются через `detector/engine/registry.py`:
`yamnet` зарегистрирован по имени, сторонние классы можно зарегистрировать
программно или передать как dotted path в `--engine`. Класс без manifest
остаётся доступен через старый интерфейс с предупреждением. UDP Hub — отдельный сетевой relay.
`RuntimeMessage` оборачивает legacy payload и не
фиксирует финальную публичную схему `v1`.

Рекомендуемый путь миграции:

1. Описать текущие score/event и audio wire formats и сохранить примеры как
   legacy профиль.
2. [x] Ввести внутренний `audio-frame.v1` и SDR1 input adapter, оставив
   сетевой формат SDR1 без изменений.
3. [~] Вынести YAMNet + MLP inference в stage с `inference-result.v1`; отдельно
   извлечь DSP/буферы и оформить регистрацию цепочки как pipeline provider.
4. [~] Вынести текущую event policy и storage клипов; определить общий контракт
   policy и output adapters для событий.
5. Добавить конфигурируемый routing и второй независимый компонент; затем
   обновить UI и публичные API управления.

Такой порядок позволяет проверять каждый новый контракт на существующем
YAMNet + MLP без одновременной замены транспорта, модели и интерфейса.
