## 9. Локальный inference на ESP32-S3 — новый подход: DSP-фичи

Проблема спектрограммного подхода: модель зависит от АЧХ микрофона →
при смене микрофона/локации ломается. Новый подход: **микрофонно-инвариантные
DSP-фичи** (pitch, energy, centroid, HNR, ZCR) → rule-based или tiny CNN.

### DSP Feature Extractor (Python → затем C для ESP32)
- [x] Реализовать DSP feature extractor на Python (`ml/dsp_features.py`):
  pitch (YIN), RMS energy, spectral centroid, HNR, ZCR,
  spectral bandwidth, spectral flatness, spectral rolloff — 8 фич на фрейм.
- [x] Прогнать extractor на имеющемся датасете, собрать статистику фич по классам.
- [ ] Визуализировать фичи для каждого класса (siren sweep, explosion spike,
  UAV harmonics) — `--plot` флаг готов.
- [ ] Валидировать: фичи действительно инвариантны к микрофону (сравнить
  INMP441 vs колонка vs ESC-50).

### Rule-based Detector (Вариант A — слабый базелайн)
- [x] Siren: centroid autocorrelation + sweep detection.
- [x] Explosion: RMS скачок + спад + centroid.
- [x] UAV: sustained energy + spectral stability.
- [x] Измерить accuracy rule-based: **siren P=0.26 R=0.28, explosion P=0.38 R=0.20,
  UAV P=0.69 R=0.18** — правила недостаточны через шумный INMP441.

### Tiny Conv1D на DSP-фичах (Вариант B — основной подход)
- [x] Обучить Conv1D на 8+8 фичах × 250 фреймов (5 с). Архитектура:
  Conv1D(24,k=7) → Pool → Conv1D(48,k=5) → Pool → Conv1D(48,k=3) →
  GlobalAvgPool → Dense(48) → Dense(4). Итого: **18K параметров**.
- [x] Квантизовать в INT8: **30 KB** TFLite модель.
- [x] Val accuracy: siren 58%, background 92%, explosion 81%, UAV 76%.
  Модель в ~600× меньше YAMNet+MLP (30KB vs 17MB).
- [ ] Добавить mixup и дополнительную аугментацию для улучшения siren accuracy.
- [ ] Сравнить DSP CNN vs YAMNet+MLP на тех же данных (side-by-side).

### Каскад DSP → YAMNet (деплой на RPi)
- [x] Создать `detector/dsp_features.py` — runtime-версия экстрактора (numpy only).
- [x] Создать `detector/dsp_infer.py` — TFLite inference + rolling feature buffer.
- [x] Интегрировать DSP pre-filter в `yamnet_engine.py`:

- [x] Обновить `docker-compose.yml` — пути к DSP модели.

## Открытая архитектура и несколько ML/LLM-решений

Цель: пользователь может подключить своё или стороннее решение распознавания,
сначала вместо текущего YAMNet + MLP, а затем — несколько решений параллельно
или каскадом. Общий тракт аудио, события, UI и интеграции при этом остаются
независимыми от конкретной модели. Текущий `EngineInterface`, Runtime Hub и
`EventBus` — стартовая точка; пока запускается один engine через `--engine`.

Важно различать программную шину сообщений (`EventBus` / контракты данных) и
аппаратные аудиошины или драйверы. ML/LLM-движку, который получает готовое аудио
от Detector, драйвер микрофона не нужен. Поддержка нового физического источника
(I²S, USB/ALSA, сетевой поток и т. п.) — отдельный адаптер входа, который
публикует общий формат аудиоданных.

### План следующего инкремента: конфигурация нескольких решений

Хранимый контракт `engine-graph.v1` зафиксирован; UI и запуск нескольких
движков реализуются отдельными шагами. Форма в `settings.json`:

```json
{
  "engine_configs": {
    "yamnet": {
      "selector": "yamnet",
      "enabled": true,
      "settings": {"siren_threshold": 0.1}
    },
    "energy-threshold-example": {
      "selector": "detector.examples.energy_threshold_engine.EnergyThresholdEngine",
      "enabled": false,
      "settings": {"energy_event_threshold": 0.08}
    }
  },
  "engine_routes": {
    "default": ["yamnet"],
    "by_source": {"0": ["yamnet", "energy-threshold-example"]}
  }
}
```

Семантика для MVP: `engine_configs` — словарь по стабильному `engine_id`;
`selector` — зарегистрированное имя или локальный Python entrypoint; отключённые
решения не запускаются. `engine_routes.default` назначает решения всем источникам,
для которых нет отдельного правила; `by_source` полностью переопределяет список
для указанного `source_id`. Маршрут может содержать только включённые и
сконфигурированные `engine_id`. Секреты внешних сервисов в этот JSON не класть.

Сохранять обратную совместимость: если `engine_configs` отсутствует или пуст,
работает прежний одиночный `--engine` и старые плоские настройки. При активном
графе источником выбора движков служит graph; явный `--engine` возвращает ясную
ошибку. Per-engine значения накладываются на legacy defaults, `settings.json`
автоматически не мигрируется.

Рекомендуемый порядок реализации:

1. [x] Описать и валидировать структуру `engine-graph.v1`, настройки по JSON
   Schema draft из manifest и ссылки маршрутов; неизвестные graph/entry поля
   сохраняются, ошибки типов возвращаются API как `400`.
2. [x] Добавить хранение `engine_configs[engine_id].settings` и маршрутов через
   `/api/engine-graph`; старые плоские настройки остаются fallback. Неизвестные
   поля сохраняются.
3. [x] Runtime Hub применяет default/by-source маршруты к подпискам движков;
   Settings UI позволяет назначать маршруты по умолчанию и источникам.
4. [x] Запускать назначенные графом движки ровно один раз с manifest и
   отдельными settings; повторный запуск одного entrypoint запрещён. В graph mode
   YAMNet хранит настройки и smoother state локально; повторные экземпляры той
   же реализации пока запрещены.
5. [x] Передавать обязательный `engine_id` в `InferenceResult`, выбирать event
   policy по движку и передавать policy настройки конкретного graph entry без

   сообщения содержат `engine_id`.
6. [x] API показывает локальные manifests и сохранённый graph и валидирует
   JSON Schema draft из manifest; UI показывает недоступный selector,

7. [x] Settings-раздел «Решения» поддерживает включение, manifest settings,

8. [x] Добавлены регрессионные проверки миграции старого `settings.json`, legacy
   dotted `--engine` и его явного запрета при активном graph, enabled/disabled
   validation, default/by-source маршрутов, неизвестного источника, доставки через
   Runtime Hub, независимых settings и отказа одного движка. `main()` проверен
   с реальными UDP, Uvicorn/FastAPI, API и тестовым manifest engine.

Ограничения первого multi-engine MVP: маршрутизация статическая, каскадов и
слияния результатов нет; несколько экземпляров одного stateful implementation
не разрешать, пока буферы, policy и mutable settings не изолированы по ID.
